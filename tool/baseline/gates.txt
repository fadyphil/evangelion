# reader tells a STRENGTHENING from a LOWERED floor: 2541 → 3691 → 3744 → 3634,
# with coverage rising or holding at every step, and every re-recording taken
# from a GREEN run. A bare `test_count` line cannot say that, and the next
# re-recording would have had nothing to point at.
#
# ## `uncovered_lines` IS THE FLOOR, AND `coverage_pct` IS NOT
#
# The floor is now a **budget of uncovered lines** — an integer — and the
# percentage beside it is a rendering of that budget at the tree's current
# size, not the budget itself. The comparison gate 7 makes is
# `uncovered <= uncovered_lines`, exactly.
#
# **WHY A PERCENTAGE WAS NOT ENOUGH, and this is not a story about rounding.**
#
# **A PERCENTAGE FLOOR WIDENS ITSELF AS THE CODE GROWS.** 98.85% of 8601
# lines is 99 uncovered lines; 98.85% of 8701 lines is **100** — so adding a
# hundred *covered* lines silently admitted one more uncovered line, without
# anybody deciding to admit it. A budget of uncovered lines does not move when
# the code grows, so "no new uncovered code" means the same thing on Tuesday
# as it did when the floor was recorded.
#
# **AND THE MEASUREMENT IS A SAMPLE, SO A PERCENTAGE OF IT WAS A NUMBER NO
# RUN PRODUCED.** `flutter test --coverage` collects from **one isolate per
# isolate group** (`package:coverage` 1.15.1's `coveredIsolateGroups`),
# because the VM shares program counters between the isolates of a group.
# **A `const` CONSTRUCTOR IS NOT A PROGRAM COUNTER** — materialising a
# canonical constant is a *per-isolate* event — so the line recording a
# materialisation is reported as covered or **not** depending on which isolate
# the collector sampled.
#
# **MEASURED, 2026-10-20, on one tree, one line** (`eva_motion.dart:1046`, the
# `const EvaShake();` declaration):
#
#     16-core machine, default concurrency   4
#     the same tree, --concurrency=2         2
#     the CI runner                         0
#
# That single line was the **whole** of the difference between the runner's
# 8501/8601 and the local 8503/8601, and it is why the runner measured 98.84%
# against a floor of 98.85% for three consecutive runs — and why the floor was
# compared with a ROUNDED percentage, which is the only reason a number no run
# produced could pass at all.
#
# **THE FIX WAS NOT A TOLERANCE.** A tolerance is a floor that is not a floor,
# and this file exists to stop that. The fix was that `EvaShake` — the
# design system's own shake curve, `redesign.html:360`'s `@keyframes shake`,
# used by `/login`'s `.cta.err` and the quiz's `.opt.wrong` — **had no test of
# its own**. It was covered only incidentally, by whichever test happened to
# build one of those two screens and run the animation, and nothing asserted
# a single number about it. AGENT_CONTEXT §6 requires red-first for motion
# tables, and a motion table with no test is a table nobody is holding up. It
# has one now: the four waypoints, the two ends, the interpolation between
# them, the duration, and the band.
#
# **3633 → 3639 tests, and 99 uncovered lines, with the floor's PERCENTAGE
# UNCHANGED at 98.85.** The count rises to the suite's own size, which is a
# **strengthening** — a run that lost a test is now red rather than merely
# smaller. The coverage floor is **not** lowered: 99 uncovered lines is what
# the CI runner measured on this tree, and the local machine measures 98, so
# the floor admits both and is not one line wider than the worst of them.
#
# **3639 -> 4030 tests, and 98.85% -> 99.13%, with the servant/admin portal.**
# The test-count floor sat **391 tests below the suite's own size**, which the
# history above calls "toothless" - a run that lost three hundred tests would
# still have passed gate 6. The portal brought its own suites (the servant
# feature, the role mechanism, four new gates, and two reviews' fixes), and
# this re-recording takes the floor up to the suite's size again. It is a
# **strengthening**: the count rises to what the suite really is.
#
# **AND THE UNCOVERED-LINES BUDGET DID NOT MOVE, and that is the stronger
# statement.** The portal added roughly nineteen hundred lines of new code and
# the measurement came in at **89 uncovered** - *under* the existing budget of
# 99, with the budget untouched. That is the budget working exactly as the
# section above describes it: "a budget of uncovered lines does not move when
# the code grows, so 'no new uncovered code' means the same thing on Tuesday as
# it did when the floor was recorded."
#
# **THE ONE NUMBER MEASURED ON THE LOCAL MACHINE ALONE IS THE UNCOVERED COUNT,
# AND THE LOCAL MACHINE IS THE OPTIMISTIC ONE.** This file's own measurement
# above is that the CI runner covers *fewer* of the `const`-materialisation
# lines than a local machine does - 16 covered hits locally at default
# concurrency, 2 at `--concurrency=2`, **0 on the CI runner** - so the runner's
# uncovered count is the **higher** one. The floor was written to the **worst**
# of the two ("not one line wider than the worst of them"), and the local 89 is
# the best of them.
#
# **And the portal made that gap bigger, not smaller.** It added eleven
# `freezed` entities, three cubit states and a controlled field, and every one
# of them is a `const` constructor whose materialisation is a per-isolate
# event - the very thing the measurement above is about.
#
# So the budget stays at **99**. Writing 89 would be a tightening of eight lines
# that no measurement on this tree supports, and it is exactly the mistake this
# file's own history warns about.
